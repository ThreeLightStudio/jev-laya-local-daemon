Why this exists

Start Laya once. Use it from any local app.

Laya normally runs inside Python. Without laya-local-api, every project would need to load the model and manage Python itself. This project moves that work into one small local server that stays running and can be shared by your other apps.

The surprising part When I copied Jev's multiplexed state shape into Laya, Laya dropped to 4 / 16.

Laya works well when each decision receives only the state it needs. Packing many independent cases into one shared object and asking each question to inspect state.case_XX caused nearly every answer to collapse toward reanalyze. Four-case mixed batches showed the same pattern, so this was not only a long-context effect.

Speed numbers are not an apples-to-apples benchmark: Laya ran locally on Apple Silicon while Jev ran on TypeSafe infrastructure, and the request shapes differ. The accuracy and robustness results are more useful observations here than raw latency.

Jev's probabilities separated the clear Noul cases extremely well, but the ambiguity round also exposed a caution: it still returned 0.97–0.99 confidence on three of four deliberately debatable cases. Laya was much less certain there, although its top choices also failed to match the preferred action. Probability sharpness and calibration should therefore be evaluated separately from top-1 accuracy.

Upstream Laya reports a different ordering on its own typed-decisions benchmark: Laya typed-decisions 0.766 accuracy vs Jev 1.13.0 at 0.727. That benchmark and this small developer-tool test measure different domains, which is exactly why I treat the result here as a product experiment rather than a universal ranking. How to use it

Let normal code gather facts. Give Laya one clear, small decision.

The model worked best after the app had already gathered the facts and turned them into a short, clear description of the current situation.

1 Gather facts

Git state, tests, known changes, how old the analysis is.

→
2 Explain them simply

Use simple templates to turn raw facts into short sentences.

→
3 Ask Laya

Ask it to pick one option, rate something, or answer yes/no.

→
4 Decide what to do

Your app owns the cutoff, fallback, and final action.

“Code gathers the facts. Simple templates explain what they mean. Laya handles the small decision. Your app decides what to do with the answer.”

Good case / bad case

The shape of the state matters more than I expected.

Good case

One small state with one clear job.

{
  "tests": "47 tests are failing",
  "analysis": "fresh"
}

→ choose next action
  • Short semantic state with the meaning already made explicit
  • A small fixed choice set such as retry / inspect / test
  • Multiple questions that genuinely refer to the same state
  • Deterministic facts computed in normal code first
Bad case

Many unrelated states hidden inside one large object.

{
  "case_01": { ... },
  "case_02": { ... },
  "...": "...",
  "case_16": { ... }
}

→ "consider only state.case_07"
  • Asking Laya to isolate an independent nested sub-state by instruction
  • Large mixed contexts containing unrelated decisions
  • Raw flags and numbers whose application meaning is implicit
  • Long reasoning chains or open-ended generation

Maker's take · subjective

Jev looks stronger out of the box. Laya is interesting for a different reason.

Across these product-shaped tests, Jev is currently the stronger default for hosted typed decisions: it was more accurate on Choice, much cleaner on Noul, substantially better on Score, and more robust to paraphrasing and option order. Laya is still interesting when decisions must stay local, avoid a network dependency, and run repeatedly over small controlled states — but I would preprocess the state aggressively, tune thresholds, and keep each decision narrow.

That is my conclusion from this small experiment, not a general benchmark claim. The result may change with different domains, prompts, hardware, or future model versions.
